# 面试讲解与自检

## 60 秒介绍

“我做了一个采购到货分析原型，使用合成的订单、物流、收货数据和 SOP。用户可以询问某个订单的到货情况，系统通过工具查询数据，使用规则识别逾期、ETA 延期和物流异常，再检索处理规范，生成可追溯的报告。项目保留了无密钥 Demo 和云端模型工具调用接口，目前完成固定样例验收与模拟协议测试，真实云模型评测待运行。这个项目主要让我练习 Agent 工具设计、状态管理、证据约束和评测。”

这段介绍只适用于已理解并验证相关代码的情况。不要把仓库生成过程、尚未完成的 Cloud 测试或没有参与过的企业流程写成个人经历。

## 六个值得讲清的问题

**1. 为什么不直接把数据库内容全部交给模型？**

工具可以明确读取范围、统一时间截断与数量计算，并保留可追溯记录。模型上下文不需要包含无关订单。代价是需要设计工具接口与规则，并处理多步调用失败。

**2. 为什么既有规则又有 Agent？**

数量、日期和已收齐判断适合确定性代码；Cloud 模型负责选工具并从本次检索结果中选择建议原文。Demo 是同一业务流程的确定性基线，不能单凭 Demo 运行成功证明模型规划能力。

**3. 怎么处理“部分到货”？**

先汇总订单与实际收货，再分析尚未收齐批次。历史异常是否仍然有效，需要结合批次是否已收齐判断。讨论时打开 `PO-1001` 与 `PO-1006` 的实际证据，而不只背业务结论。

**4. 检索为什么可能失败？**

查询缺乏关键词、资料没有覆盖、分块丢失上下文或向量服务失败，都可能导致无有效结果。本地词法检索与语义 Embedding 的能力不同；没有检索到依据时应披露缺口，不能把任意片段当依据。

**5. 怎么避免幻觉？**

项目没有停留在“引用 ID 存在”这一层。建议必须是本次 SOP 检索片段中的完整原文行，说明只能从 `SAFE_NOTES` 中选择，事实与跟进草稿由程序生成。这能拒绝自由改写时添加的无来源判断，代价是表达和建议范围受到 SOP 限制。它不等于自由生成建议已经过语义核实，原文是否适用仍需人工检查。

**6. 怎么评估？**

分三层：业务规则测试；固定数据与预期的工作流评测；独立运行的真实模型评测。检查事实正确性、异常是否漏报 / 误报、证据是否有效、信息不足时是否合理处理。耗时和 token 是实际观测值，不能代替答案质量。

## 能对应到代码的讲解路线

1. 选一个订单，追踪 UI 请求进入 API 后如何获得订单上下文。
2. 找到数据库查询与时间截断，解释如何避免使用分析日之后的信息。
3. 打开规则测试，挑一个“已收齐但曾出现物流异常”的反例。
4. 展示一段 SOP 的检索片段与报告引用，解释无命中和缓存失效。
5. 展示一个真实工具失败或缺失字段案例，说明它如何影响状态与报告。
6. 对照一次评测结果，解释每个分数的样本范围，明确哪些尚未实测。

如果 Cloud 模式尚未亲自运行并核对，应改为“实现云端模型调用接口，实际模型评测待完成”。

目前可核对的量化结果是：“30 个独立固定验收案例通过 30 个，包含 5 个故障注入案例；真实云模型调用数为 0。”详细运行环境和测试状态见 [验证记录](validation.md)。这反映固定样例覆盖情况，不能改写成生产准确率或业务提效比例。

## 尚不应声称的能力

真实车企部署、生产采购决策、供应商自动触达、端到端业务提效、企业级安全权限，以及没有实际运行过的模型或数据库环境。这些都需要额外工程或真实业务验证。
